# 青城财神殿 · 3D 祈福互动场景

网页版互动场景。玩家登录后以卡通小人进入一座**以青城山道观为原型**的 3D 殿宇：殿内整齐列着 150 个蒲团（尺寸与间距翻倍后每排严格 10 个、共 15 排），可以走过去坐下三拜膜拜，也可以走到青铜鼎式香炉前上香。

本版本相对初版做了十二处改动：**渲染改为真 3D（Three.js / WebGL）**、**三龛金身改用用户提供的鎏金财神像照片**、**背景音乐改为道乐**、**构图由殿外立面扩展为宏大的殿内纵深空间**、**殿宇整体放大到可容纳 150 个蒲团并清空三龛头部的全部遮挡**、**修正叩拜朝向（改为面向最近神龛低头叩拜）**、**加大蒲团间距让拜台疏朗**、**可行走区域扩到殿前外庭与两廊并改为人物始终居中的跟随镜头**、**修好往后退被拜台交界与点击吸附卡住的问题**、**参考韩国 Sansa 山寺加入「同殿静默共处」的多人交互**、**按 Sansa 清缘堂重整殿内空间（暖木地板、一排排蒲团、殿门与山门收口）并把后退边界推到山门前**、**蒲团尺寸 ×2 / 间距 ×2 / 每排 10 个，并把殿宇、庭院与山门整体拉深约 2 倍以继续容纳 150 个**。

### 3.1 殿内纵深

原先的构图更像「站在殿外看神龛立面」，上方只有一条窄屋檐带。`world3d.js` 的 `buildGrandHall()` 把三龛包进一座有纵深的大殿：

| 层次 | 内容 |
| --- | --- |
| 柱列 | 两侧各两列、七进的朱栗色檐柱，柱础与栌斗齐全，配纵向旋子彩枋和金线压边 |
| 廊庑 | 两侧长墙，格扇窗与青绿山水壁画交替，顶部再压一道彩枋 |
| 天花 | 神帐上方一条横向旋子彩画带与一排垂穗金珠；三顶宝盖已移除，避免竖屏下压住财神头部 |
| 神帐 | 三龛之后的朱红褶裥帷幔，含金云纹、海水江崖与垂穗；两侧各嵌一面太极八卦圆光 |
| 中轴 | 贯穿整片拜台的丹陛石雕御道（云纹＋金线压边）、加长的望柱石栏 |
| 灯火 | 沿柱列向殿深处递减的八盏宫灯，另加高位暖光把藻井与柱列从青绿雾气里托出来 |
| 远景 | 三重后殿（三清殿／文昌殿）与山门牌坊沿中轴向山里退去，远山与七层山岚加宽加远 |

**剖顶视角的说明**：俯视相机下，完整的朝镜头前坡屋面会把殿内三龛完全挡住。因此前坡按传统界画的做法剖开，只保留后坡青瓦、正脊与左右两段极短的前檐轮廓线。这是构图取舍，不是建筑还原。固定俯视机位下神帐与后坡屋面会遮住三重后殿与山门的大部分，它们主要为不同视差／宽屏比例提供层次。

### 3.2 殿宇放大、150 个蒲团与「不遮头」

本轮按「别遮住财神的头，把整个财神殿再弄大一点，容下 150 个蒲团」改造：

- **世界放大**：逻辑平面由 1000×680 扩到 1600×900；整座建筑放进 `hall` 组统一缩放 1.5 倍，柱列、廊庑、神帐、月台石栏、丹陛御道同步向前延伸，把拜台完整包在殿内。蒲团、香炉、角色、灯笼仍以 1:1 落在世界坐标里，不受建筑缩放影响。
- **150 个蒲团（历史演进，当前参数见 3.6）**：这一阶段是东西两片各 10 列 × 7 行 = 140 个 + 龛前 10 个上座 = 150 个，列距 74 / 行距 76 / 直径 52，中轴御道 160。后续已按「尺寸 ×2、间距 ×2、每排 10 个」重排为 15 排 × 10 个，殿宇同步拉深，但落座点 `canStand()` 校验与实例化渲染机制未变。
- **实例化渲染**：150 个蒲团若逐个建 Mesh 会产生约 450 个 draw call，实际用两个 `InstancedMesh`（侧面 + 顶面）加一个跟随高亮环，共 3 个 draw call。占用状态通过 `instanceColor` 变暗，只在状态变化时刷新 GPU。因此蒲团数量从 12 增到 150，桌面 draw calls 反而由 728 降到 611。
- **清空头部通廊**：删除横贯三龛的前檐额枋与金线、把前檐轮廓线改成左右两段、四根前檐柱全部移到放大后 |x| ≥ 510、六盏灯笼退到 |x| ≥ 440、移除三顶宝盖改作帐前垂穗。三尊财神的官帽、帽翅与长须在桌面与竖屏下均完整无遮挡。
- **殿额归位**：「財神殿」匾额移到像顶之上的窄带。实测桌面投影中心 y≈41 / 中尊像顶 y≈99，手机 y≈151 / 像顶 y≈212，两端都有余量；匾额材质关闭深度测试并向镜头微倾，竖屏陡俯角下也不会被后坡屋檐压成一条空线。
- **登录页相机**：桌面 dist 1500 / fov 42 / pitch 0.70，竖屏 1860 / 50 / 1.00。机位拉幅小于建筑增幅，殿体在画面里更饱满，同时 150 个蒲团仍能同框。进庙后切换为跟随镜头，见 3.4。

### 3.3 拜对方向：朝向神龛低头叩拜

先前坐下时虽然是「背对镜头」，但叩拜动作的 `pivot.rotation.x` 取了正值。角色已绕 Y 转约 π（脸朝殿内 −Z），在 Three.js 的 Euler XYZ 顺序下再绕世界 X 轴取正角会把脸抬起来 —— 实测世界朝向向量为 `[0, +0.49, -0.87]`，即**仰头后倒**，看起来像拜错方向；同时转身用每帧 0.22 的缓动，软件渲染低帧率下还没转到位就开始叩拜。

本轮修正：

- `player.js` 新增 `facing`（弧度）：落座与上香时取 `facingToShrine()`，按**最近一龛财神**的位置，以 π 为基准叠加一个受限偏角（0.7 倍 `atan2`），两侧蒲团上会自然斜朝神龛；`dir='up'` 保留给 2D 回退路径。
- `world3d.js` 的 `poseCharacter` 优先使用 `facing`，且 `sit / worship / incense` 三种定姿动作**立即转正**，走动时才保留缓转。
- 叩拜的 `rotation.x` 改为 **负角**（`-bow * 0.44`），头往 −Z 低下去；幅度收敛到 0.44 倍，避免俯视相机（约 38°）叠加后把后脑勺与袍身压成一个锥形。上香同步改为微微前倾，叩拜时名牌抬高避免盖住头顶。

实测结果（坐在中轴右侧蒲团）：坐下 `face=[-0.19, 0, -0.98]`（朝殿内并略偏向最近的中尊），叩拜 `face=[-0.19, -0.22, -0.96]`（低头朝财神），`rotX<0`；坐在正对中尊的蒲团上坐下朝向为 `[0, 0, -1]`。作为对照，修正前叩拜是 `[0.01, +0.49, -0.87]`（仰头后倒）。证据见 `../04_verification/pose-report.json` 与 `shot_pose_sit.png`、`shot_pose_worship.png`。

### 3.4 扩大活动区域与「人物一直居中」的跟随镜头

本轮按「让能活动的区域变大，然后人物一直居中」改造。关键约束是**不破坏上一轮的成果**：1600×900 逻辑平面、150 个蒲团坐标、三龛位置、殿宇 1.5 倍缩放与叩拜朝向全部不动。

- **区域扩展**：`config.js` 的 `WALKABLE` 由 4 个矩形（约 94.8 万平方单位）改成 7 个连通矩形（**264.1 万**，约 2.8 倍）：殿内拜台、龛前横廊、东西廊庑、殿前月台与外庭、两个后角。外庭向下再延到 `y=1340`，`WORLD = {minX:-250, maxX:1850, minY:170, maxY:1340}`。逻辑坐标允许超出原平面，`wx()/wz()` 会自然映射到更远的 3D 世界坐标，因此既有对象一个坐标都不用改。
- **出生点**移到殿前外庭 `(800, 1080)`，玩家从山门方向一路走向拜台，直观感受到空间变大。三龛须弥座新增圆形障碍，防止角色穿进金身。
- **3D 跟随镜头**：登录页仍是原来的宏大全景；进庙后 `followOn=true`，相机恒定挂在玩家正后上方、`lookAt(px, 60, pz)` 锁定角色，桌面 fov 48 / dist 1250 / pitch 0.60，竖屏 52 / 1350 / 0.68。**严格逐帧对齐、不做平滑滞后**（低帧率下平滑会让角色偏离中心 130px 以上），鼠标视差在跟随模式下关闭。实测 8 个位置（含外庭两角与两廊）投影偏移均为 **0.00px**。
- **点击命中不变**：`screenToLogical()` 用射线与地面求交，相机移动后自动适配；`project(x,y,0) → screenToLogical()` 往返误差实测 **0.00**。粒子与功德浮字仍用 `project()` 叠加。
- **2D 回退**：`main.js` 的相机改为双轴严格居中（scale 放大到 1.6 / 竖屏 2.0 才有平移空间），暗角与边框改屏幕空间，并在静态底图之外铺满外院青石地与石缝，走到殿外不会露出空白。
- **外庭造景**：`buildEnvironment()` 加铺一层 3600×2800 的外院地面、三级月台石阶、两侧望柱石栏、四面八卦地雕、四座石灯、矮照壁与松柏。**刻意不放高墙与近处高树**——相机始终在玩家正后方，任何高物体都会横在相机与主角之间挡住画面。

取舍：跟随镜头把人物钉在画面正中，因此站在最远的外庭时殿额与金身上缘会贴近画面上沿；走到拜台（实际膜拜位置）三龛金身、匾额与楹联即完整入画，且没有任何物体遮挡头部。竖屏仍会裁掉左右最外侧画面。

### 3.5 「往后退不了」的修复

竖屏实测发现，角色退到中轴御道那块浅色石坪附近就再也不动，底部还一直挂着「正在走向指定位置…」。原因是两处叠加：

1. **连通带真空**：`canStand()` 原先给每个可行走矩形都内缩 6 单位，而相邻矩形只重叠 10 单位，于是拜台→外庭（`y≈885`）、拜台→西廊（`x≈45`）、拜台→东廊（`x≈1555`）各留下 2 单位站不住的窄缝。步长较小的帧会恰好停在缝上，键盘、摇杆、点击寻路一起被卡住。现在**缓冲只留在外接框上**，内部矩形按原始边界判定，重叠带保持完整连通。
2. **点击吸附退回原地**：跟随镜头的相机挂在玩家正后上方，点击画面下半部换算出的逻辑点在身后几百单位，竖屏最底部甚至是 `y≈1444`，远超外庭边界；而 `snap()` 只在 160 半径内搜索，找不到就把目标设为**角色当前坐标**，于是弹出走路提示却原地不动。现在改为：就近吸附失败后，沿「玩家 → 点击点」方向逐段探测，取连续可达的最远一点，让角色走到外庭边界；外庭也向下多留 120 单位退路。确实无处可去时直接提示「那边已经走到头啦」，不再进入寻路状态。到达后收掉走路提示，手动输入打断寻路时也同步改文案。

`index.html` 里所有脚本与样式加了 `?v=15` 版本号（v13 → v14 多人版 → v15 Sansa 布局版），避免浏览器沿用旧缓存让修复看起来没生效；后续再改 JS 时记得同步递增。

| --- | --- | --- |
| `presence` | `client_id` 主键；昵称、衣色、x/y、pose/dir/facing、功德/叩拜、`greeting_at`、`updated_at` | RLS 开启；`anon`/`authenticated` 公开读、可 upsert；无 DELETE 权限 |

两张表只存**展示用的临时状态**，没有账号、手机号、邮箱或任何隐私字段；应用只 upsert 自己的 `client_id` 行。免注册带来一个明确取舍：匿名角色无法用 `auth.uid()` 做行属主校验，因此写策略是公开的；最坏情况只是别人恶搞在线位置，不影响任何人的资产或身份。超过 **20 秒**没上报即视为离殿，旧行不删除、只靠查询过滤。

**前端**

- `js/multiplayer.js` 用 CDN 的 `@tencent-ai/workbuddy-cloud-sdk@dev` IIFE 构建动态加载（纯 HTML 项目不引入打包器），`endpoint` / `publishableKey` / `oauthRelayBaseUrl` 全部来自激活返回的 `publicConfig`，不从 `location` 推导 —— 服务端按 Origin 精确校验。
- 进庙这一刻才 `start()`，登录页不产生任何云端写入。每 **3 秒** upsert 自身状态、每 **3.2 秒**拉取同殿列表与 30 秒内的新合掌；同屏最多 **60** 位真人香客。
- 随机道号为「形容词 + 的 + 名词」（如「清澈的松风」「无事的炉烟」），输入框留空即自动赐号，「换一个」可重抽；`client_id` 存 localStorage，刷新后保持同一身份。
- `world3d.js` 新增 `remoteChars` 角色池，复用 `makeCharacter()` 渲染真人，位置逐帧插值（心跳 3 秒一次，不插值会一格一格跳）、显示道号名牌、同步叩拜／上香／合十姿态；离殿即移除并释放名牌贴图。2D 回退同样绘制 `scene.remotes`。

- **功课与放空**：每次叩拜累计「百八拜」、按 B 拨一颗念珠（配木鱼音效），满 108 归零重来；按 Z 进入放空，数字与提示淡出、控件仍可用，随时「回来」。HUD 文案用「功德 +1，班味 −1」呼应打工人梗。竖屏右上角默认折成一条小胶囊，点开才显示功课与按钮，避免压住财神像。

### 3.7 按 Sansa 清缘堂重整殿内空间（并修好「还是后退不了」）

多家报道对 Sansa 的「清缘堂」描述一致：**开放式木造法堂、正中央金色大佛、地上铺满一排排参拜垫**，每间最多 100 个蒲团；殿外才是松林庭院与石板路；点「礼拜」小沙弥会自己走进法堂找空蒲团、面向佛像礼拜。本轮保留三龛、150 个蒲团与青城道观的喜庆视觉，只改**空间组织方式**。

## 五、道乐（重要：这是合成，不是录音）

`js/audio.js` 是一段**原创的 WebAudio 程序合成**，不含任何录音采样，也不发起网络请求。原因是检索到的真实道乐录音（全真正韵、上海道乐、青城山道乐器乐曲等，见 `yinyue.daoisms.org` 与 `daoisms.com.cn`）没有可核验的开放授权，不适合直接打包进交付物。

音乐构成：

- 法器层：引磬（非谐泛音列 + 长尾）、木鱼、云锣／铛子、法鼓；
- 旋律层：笙箫（慢起音、气声与颤音）、古琴（拨弦 + 泛音）；
- 旋法与节奏：羽调式五声音阶、级进为主的「步虚」式旋律，0.62 秒一步、64 步一循环的慢板，一板三眼；
- 空间感：程序生成的 2.4 秒脉冲响应卷积混响，模拟殿堂回响。

音效也一并改成法器质感：叩拜=引磬、落座=木鱼、功德里程碑=法鼓+云锣、礼成=磬+云锣；原先的鞭炮音效已移除。UI 与帮助文案中的「喜乐」已改为「道乐」。

**若需要真实道乐录音**：把有授权的音频文件放进 `assets/`，在 `audio.js` 里用 `AudioContext.decodeAudioData` + `AudioBufferSourceNode`（`loop = true`）替换 `update()` 里的合成调度即可；`play()` 的音效可保留不变。

浏览器要求音频由用户手势触发，所以道乐从点击「进庙祈福」之后才开始播放。按 M 或点右上角「道乐」开关可切换。

## 九、已知限制

1. **背景乐是合成道乐，不是真实道观录音**，原因见第五节。若需要真实录音，需自行提供授权音频。
2. 没有真机测试记录。手机端结论来自 Chrome 390×844 触摸模拟，不等同于 iOS Safari 或安卓 WebView。
3. **没有账号／登录系统**：按 Sansa 的零门槛设定，云端只同步在线位置、姿态与合掌事件；昵称与 `client_id` 存在浏览器 localStorage，功德、香火、百八拜、念珠仍是本轮会话内的本地数值，不跨设备同步。
4. 自动寻路仍是直线加侧向绕行，不是 A* 寻路。
5. 竖屏会水平裁掉左右最外侧画面；跟随镜头只显示玩家周围一段，远处蒲团与香炉需要走过去（或用「膜拜」「上香」按钮自动寻路）才进入视野。
6. 前坡屋面按界画方式剖开，是有意的构图取舍；三龛金身是带厚度的贴图立像，不是可 360° 环视的圆雕模型。
7. 殿额关闭了深度测试，因此在极端视差下会绘制在屋檐之前；它固定在画面顶端、不覆盖三龛区域，属于为保证竖屏可读性做的取舍。
8. 逻辑测试的 49 项断言覆盖的是状态机与输入层；3D 旋转的实际几何方向由 `pose_check.js` 读取世界朝向向量、镜头居中由 `camera_check.js`、连通带与后退寻路由 `backmove_check.js`、蒲团与殿宇布局由 `sansa_layout_check.js` 在真实浏览器里验证，四者不互相替代。
9. 殿宇拉深后（桌面 39332 / 手机 26636 三角形），蒲团实例化让 draw calls 保持在桌面 520 / 手机 184。真机 GPU 无压力，软件 WebGL 下仍偏慢；低端设备可优先删减 `buildGrandHall()` 里的柱列进数与三重后殿。
10. 三重后殿、山门牌坊与远山在登录页的固定俯视机位下大部分被神帐与后坡屋面遮住；跟随镜头下它们只在玩家走向殿后时才进入画面。上香链路仍主要由无头逻辑测试覆盖，浏览器端这轮点击验证的是蒲团膜拜链路。
11. WebGL 不可用时的 2D 回退画面仍按初版 1000×680 版式绘制，扩大后的逻辑平面下会有构图偏移；跟随镜头与外院铺地已补齐，功能逻辑不受影响。2D 严格居中放大后，远处热点可能落到视口之外，此时请用 E / F 键或动作按钮自动寻路。
12. 人物被钉在画面正中后，退到山门（`y≈3420`）时三龛金身已远在画面之外；走到龛前拜台三龛金身、匾额与楹联即完整入画，且没有任何物体遮挡头部。这是「一直居中」与「远眺全殿」之间的取舍，也对应 Sansa「殿内看佛、殿外看门」的空间层次。竖屏跟随镜头视野更窄，站在法堂中段时三龛可能只剩下半身，登录页全景或走近后可见完整金身。
13. 云端按 Origin 精确校验，**只有正式分享域名下才能连通**；本地 `file://`、`127.0.0.1` 或任何别的域名打开都会显示「独拜」，这是预期行为而不是故障。
14. 15 排蒲团沿纵深铺到 `y=2543`，从山门 / 出生点走到龛前香炉约 2100 逻辑单位（按 `SPEED=330` 约 7 秒），比上一版明显更长；想快速参拜请用「膜拜」「上香」按钮或 E / F 键自动寻路。这是「保住 150 个 + 每排只放 10 个」必然带来的空间代价。
14. 在线状态用轮询（上报 3 秒 / 拉取 3.2 秒），不是 WebSocket 实时通道，别人的位置最多延迟约 3 秒；同屏上限 60 人。`presence` 表不给客户端 DELETE 权限，过期行靠 20 秒 TTL 查询过滤，会缓慢累积，必要时在云端管理面板清理。
15. 免注册意味着两张表是**公开读、匿名可写**，没有 `auth.uid()` 属主校验。表内只有临时展示状态、无隐私数据，最坏情况是在线位置被恶搞；若需要防滥用，得引入登录并改成 owner-scoped RLS，那会牺牲「打开即入殿」的零门槛。
16. 多人同殿版已于 2026-11-14 覆盖上线，线上端到端验收 26 / 26 通过。跨身份可见性用两个不同 `client_id` 的浏览器视口验证了「一方写入、另一方拉取并渲染」，但这仍是同一台机器上的 CDP 视口，不等同于两台真机／不同网络下的实测。验证产生的测试行已由云端管理通道清理，TTL 之外的离线行不会被查询到、也不会显示在殿里。
17. **本轮的 Sansa 布局与后退边界修复仍是本地版（`?v=15`），线上分享链接是上一版多人同殿版**：外庭边界仍为 1340、没有暖木地板与山门，因此线上用户在 `(800,1334)` 仍会退不动。按发布规则需要再次明确要求覆盖发布，才会把本轮改动同步到线上。
